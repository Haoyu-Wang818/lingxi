# 2026-11-21 I2 拍板书到卡片

## 目标

一张板书变成一组卡片：拍照或相册导入 → 端侧 OCR → 云端整理（笔记、知识点、关系、卡片）→ 写库 → 进入复习；断网时进入队列，联网后自动补做。

需求（trace.py ITERATION["I2"]）：FR-CAP-01、02、03、06，FR-NOTE-01、03、04、06，FR-KG-01，FR-AI-04，FR-GW-01、02、06，FR-REV-01、10、11；另含 FR-AI-05、FR-WEAR-08。

## 先做的验证（接 I1）

- `server/.env` 中的变量名是百炼文档的 `DASHSCOPE_API_KEY`，网关原来只认 `LLM_API_KEY`。改为两个名字都接受，没有改动用户的 `.env`，key 的内容从未输出。
- 真实调用：`/v1/chat` 约 3 秒，`/v1/extract`（309 字）约 18 秒，返回结构合法；模拟器设置页问答成功并有执行记录。

## 关键决策

- **端侧 OCR**：PP-OCRv4 mobile 的 ONNX 版本 + ONNX Runtime（ADR 0003）。
  - DB 文字框提取、CTC 解码、阅读顺序、深色板书反色都用纯 Kotlin 实现，可以在 JVM 上单测。
  - 模型约 16 MB，不进 git，由 `scripts/fetch_models.sh` 按固定 SHA-256 下载。
- **速度**：让模型一次输出全部内容约 2000 token，qwen-plus 要 40 秒左右。改为在网关拆成并行的短调用：
  - 笔记与知识点抽取同时进行；
  - 抽取完成后每个知识点并行出卡；
  - 全部使用 qwen-flash；打开拍照页时预加载 OCR 模型。
  - 结果：端到端中位数 12.7 秒（9 次全部 ≤ 15 秒）。
- **卡片质量**：网关做规则校验，与 core:quality 规则一致：
  - 一卡一知识点，卡片继承来源；
  - 题干与答案长度上限；
  - 单选题 2–4 个不重复选项、恰好 1 个正确；挖空题恰好一处；判断题答案以「正确 / 错误」开头；
  - 手表版题面 ≤ 20 字、答案 ≤ 12 字，且不能含挖空标记；
  - 每个知识点至少 1 张判断或单选题，缺少时重试一次。
- **关系方向**：qwen-flash 常把 PART_OF 和 EXAMPLE_OF 写反。提示词改为「from relation to」读成一句话，并给出例子，之后方向正确。
- **一次请求**：手机端只调用一次 `/v1/extract`（`with_cards=true`），网关内部完成编排。另外提供 `/v1/cards`，用于对已有知识点补出卡片。

## 模拟器走查时发现并修复的问题

1. **整批卡片为 0**：手机发送的文本段 id 是「UUID#L1」，模型会改写长 UUID，导致所有知识点都没有来源，卡片按「必须带来源」规则全部丢弃；重试又让耗时翻倍（19.5 秒）。
   - 修复：改用 `L1`、`L2`… 短 id，在本地映射回照片和行。
   - 网关在模型给出的来源无效时，按知识点名称在原文中匹配来源。
   - 没有来源的知识点不再重试。
2. **笔记 JSON 被截断**：输出上限 900 token 不够，放宽到 1500。
3. **覆盖率评测拿不到结果**：AGP 跑完仪器测试会卸载测试包，结果文件随之删除。改为在测试中把 JSON 写进 logcat，评测脚本从 logcat 读取。

## 验收结果

- OCR 字准确率 94.4%（目标 ≥ 90%），每张约 0.2 秒；见 `docs/03-test/ocr-eval.md`。主要错误是形近符号（x→×、0→O）。
- 端到端耗时中位数 12.7 秒；见 `docs/03-test/e2e-latency.md`。
- 断网导入：照片仍在手机本地识别，笔记显示「待整理」；恢复网络后 WorkManager 自动补做并生成卡片。
- 截图：`docs/03-test/screenshots/i2-*.png`。

## 人工复核

- 测试图是电脑渲染的，结果偏乐观，需要用队友提供的 20 张真实板书重新评测（SRS 验收集）。
- qwen-flash 生成的卡片质量参差，有少数挖空题较浅；笔记偶尔补充原文没有的例题。建议人工抽查 10 节课，必要时笔记改用 qwen-plus（不在 15 秒的关键路径上）。
